# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository. Note that `CLAUDE.md` is a symlink to this file, so edits here apply to both.

## What this is

Felix Schröter's personal NixOS configuration flake, managing several NixOS hosts, two OpenWrt routers, and standalone home-manager profiles, all from one repo using `flake-parts`.

## Common commands

Rebuild the local system:
```sh
sudo nixos-rebuild switch
```

Rebuild and deploy to a remote host:
```sh
sudo nixos-rebuild switch --flake '/etc/nixos#<host>' --target-host user@hostname --use-remote-sudo
```

Deploy `home-server` via deploy-rs (see `deploy.nodes.home-server` in `hosts/flake-module.nix`):
```sh
nix run .#deploy -- .#home-server
```

Check the whole flake (evaluates all outputs, runs the pre-commit hook check and deploy-rs checks):
```sh
nix flake check
```

Build a specific output (mirrors what `.forgejo/workflows/test.yml` runs in CI):
```sh
nix build .#nixosConfigurations.<host>.config.system.build.toplevel   # home-pc, home-server, cmdframe
nix build .#homeConfigurations.<user>.activationPackage               # felschr, felschr-server, felschr-work
nix build .#deconz                                                    # custom package
```

Build an OpenWrt router image:
```sh
nix build .#legacyPackages.x86_64-linux.doctr      # or .penguin
```

Format Nix files / lint shell scripts (also runs automatically via the `pre-commit` git hook, installed by `direnv`/`nix develop`):
```sh
nix fmt                 # format the whole tree
nixfmt <file>.nix       # format a single file
shellcheck <file>.sh
```

Enter the dev shell (provides the pre-commit hook setup):
```sh
nix develop
```
This repo uses `direnv` (`.envrc` runs `use flake`), so shells are usually loaded automatically on `cd`.

Update flake inputs:
```sh
nix flake update            # all inputs
nix flake update <input>    # a single input
```

There is no test suite beyond `nix flake check` / the CI builds above — correctness is verified by successfully evaluating and building the relevant `nixosConfigurations`/`homeConfigurations` output.

## Architecture

This is a `flake-parts` flake (see `flake.nix`), split into top-level modules that are imported in `outputs.imports`. Each area of the repo owns a `flake-module.nix` that contributes to `flake.*` (system-wide outputs) and/or `perSystem` (per-arch outputs):

- **`pkgs/flake-module.nix`** — custom packages (e.g. `deconz`), exposed as both `packages.<name>` and `apps.<name>`.
- **`lib/flake-module.nix`** — shared flake-level helpers exposed as `flake.lib.*`: `createSystemModule` (wraps a host's hardware+config modules and sets `networking.hostName`), `createUserModule` (from `lib/createUser.nix`; wires up a NixOS user + its home-manager profile together), `createMediaGroup`, and OpenWrt image builder helpers (`lib/openwrt.nix`).
- **`hosts/flake-module.nix`** — defines every `nixosConfigurations.<host>` (`home-pc`, `home-server`, `cmdframe`) and `diskoConfigurations`, and imports `hosts/doctr` and `hosts/penguin` (OpenWrt router image definitions built via `lib.mkOpenwrtImage`, not NixOS systems). Also declares the `deploy-rs` node for `home-server`.
- **`home/flake-module.nix`** — defines `homeModules` (reusable home-manager modules, including per-user profiles `felschr`/`felschr-server`/`felschr-work`) and standalone `homeConfigurations` for each profile.
- **`overlays/flake-module.nix`** — the single `overlays.default`, which pulls in `nixpkgs-unstable` as `pkgs.unstable`, injects locally built packages (e.g. `deconz`) into `pkgs`, and extends `vimPlugins`. Also exposes `pkgsFor system`, the canonical way every module gets an instantiated `nixpkgs` (with overlay + `allowUnfree` applied).

Additionally, `flake.nix` defines reusable `nixosModules.*` inline: `flakeDefaults`, `systemdNotify`, `inadyn`, and `caddy-authelia`. The untracked-in-flake directories `scripts/` (install/setup helper scripts, mostly shell and nushell) and `templates/` (dev-shell template, e.g. `dotnet.nix`) are not part of any flake output.

### Host composition pattern

Each `nixosConfigurations.<host>` in `hosts/flake-module.nix` is assembled from:
1. Upstream modules (`disko`, `nixos-hardware` profiles for the specific machine).
2. `self.lib.createSystemModule "<host>" { hardwareConfig; config; }`, which imports `modules/common.nix` (agenix + `flakeDefaults` + overlay wiring, shared by every host), `hosts/<host>/hardware.nix` (machine-specific, often generated by the installer — see README), and `hosts/<host>/default.nix` (the actual host config, itself composed of shared modules from `desktop/`, `hardware/`, `services/`, `system/`, `virtualisation/`).
3. `self.lib.createUserModule "felschr" { homeModule; user; usesContainers; }`, which creates the NixOS user and wires its home-manager profile (`self.homeModules.felschr*`) in one place — home-manager config is never defined ad hoc per host.

`hosts/<host>/default.nix` is a plain list of `imports` from the shared top-level directories (`desktop/`, `hardware/`, `services/`, `system/`, `virtualisation/`, `modules/`) plus host-specific config (networking, `age.secrets`, `system.stateVersion`, etc.). To see what a host actually runs, read its `default.nix` import list rather than searching for services by name.

### home-manager profiles

Three user profiles exist (`home/felschr.nix`, `home/felschr-server.nix`, `home/felschr-work.nix`) for the same physical user on different machine types (personal desktop, headless server, work laptop). They share `home/base.nix` and pull in feature modules from `home/desktop/`, `home/browsers/`, `home/editors/`, `home/shell/`, `home/services/`, `home/gaming/`, `home/modules/`. Each profile is both a `homeModule` (composed into a `nixosConfigurations` host via `createUserModule`) and a standalone `homeConfigurations.<profile>` (for use on non-NixOS or via `home-manager switch` directly).

### Secrets

Secrets are encrypted with `agenix` (`secrets/*.age`, decrypted via `age.secrets.<name>.file` in host configs). `secrets/secrets.nix` is the authoritative list of which host/user SSH public keys can decrypt each secret — update it (and re-`agenix rekey`) whenever access to a secret needs to change. New host installs need an initrd SSH key added to `secrets/secrets.nix` before secrets can be provisioned; see `README.md` for the full install/key-rotation flow.

### OpenWrt hosts

`doctr` and `hosts/penguin` are not NixOS systems — they're OpenWrt router images built through `lib.mkOpenwrtImage` (`lib/openwrt.nix`) and only exist as `perSystem.legacyPackages.<name>` outputs (`nix build .#legacyPackages.x86_64-linux.doctr`), kept out of `packages` so `nix flake check` never builds them. Configured via UCI shell snippets rather than NixOS modules.

### CI

`.forgejo/workflows/test.yml` runs on every push/PR: `nix flake check` (non-blocking), then builds `deconz`, the `home-server` toplevel, and all three `homeConfigurations` activation packages. `home-pc` is commented out of CI and `cmdframe` isn't listed at all (likely due to build cost/hardware-specific inputs) — check before assuming they're covered.

## Networking quirks (home-server / LAN)

Things that took a long time to diagnose; don't rediscover them.

- **Tailscale + Mullvad exit node**: home-server (and the main desktop) run with a Mullvad exit node active. Mullvad exit nodes don't support IPv6 (see the removed `services.nginx.resolver.ipv6` workaround in the caddy-migration commit), which caused proxy timeouts and high CPU under nginx. When testing, note whether an exit node is active: with one on the testing machine, "public" traffic leaves via Mullvad, so hairpin/LAN vs external reachability can look inverted. `ip route show default` reveals it. The exit-node fwmark workaround lives in `system/server.nix` (tailnet subnets defined in `system/vpn.nix` as `tailnet.v4/v6`); replies to tailnet destinations must keep fwmark off or they are routed out the LAN gateway and lost.
- **ts.net TLS**: `home-server.tail05275.ts.net` (and other ts.net vhosts) cannot use public ACME (no public DNS record for ts.net names, NXDOMAIN). `system/vpn.nix` issues a publicly trusted cert via `tailscale cert` (`tailscale-cert.service` + daily timer) and the Caddy vhost loads it from `/var/lib/tailscale-certs`. Caddy is ordered `after`/`wants` that service; the key is `chmod 0640` (tailscale writes 0600, caddy reads via group). Never use a blocking `systemctl reload caddy` inside that service: combined with caddy's `After=` dependency on it, that deadlocks boot and activation. The deployed script uses `timeout 30 systemctl --no-block try-reload` (commit 12044ba); generations before that can wedge caddy on restart.
- **OpenWrt routers**: reachable via tailscale (`root@doctr`, `root@penguin`); tcpdump is not installed on them.
- **Known broken (as of 2026-11): LAN/global IPv6 is broken by tailscaled's netfilter.** CONFIRMED root cause for wired paths: with `tailscaled` running on home-server (exit node configured/active), global-IPv6 unicast between LAN hosts (router↔server, and any frame whose src or dst is a global address) is dropped inside the host's own netfilter/marking; a controlled test with `tailscaled` stopped made router→server global-v6 ping work instantly, and it broke again on restart. Frames carrying only link-local addresses always pass. Wi-Fi clients additionally never receive solicited-node multicast (NS) from wired hosts even with the server's tailscaled down (remaining suspect: the client host's own tailscale/AP path, unconfirmed). Consequence: external IPv6 to home-server is broken while the exit node is used, and this matches the removed `services.nginx.resolver.ipv6` workaround comment ("Mullvad exit nodes don't support IPv6, causing proxy timeouts and high CPU"). External IPv6 itself is fine (router WAN v6 pings google at ~11 ms; non-VPN v6 from clients works), so fixing the tailscale interaction would restore external v6 to the server since Telekom routes the whole delegated `/56` to the router. Reproduction script used for the matrix (scapy on the server via `nix build -o /tmp/sc nixpkgs#python3Packages.scapy`, sending src/dst combos of link-local vs global addresses while counting `/proc/net/snmp6` `Icmp6InEchos` on the receiver).
  - **Upstream status (checked 2026-11-19)**: Mullvad exit nodes do support IPv6 since ~1.62 (v6 masquerade for WireGuard-only peers; issues tailscale/tailscale#9511 and #10777 closed Aug 2024), and current docs no longer list IPv6 as a Mullvad limitation. The old "Mullvad doesn't support IPv6" rationale for the removed nginx workaround is stale. What remains is a class of open host-side netfilter bugs around exit nodes and LAN IPv6 that matches our symptoms exactly: #19036 (IPv6 routing permanently broken around exit node use; kernel route lookup fails despite routes existing), a 2026-07 comment there (same breakage with no exit node, caused by tailscale's `::/0` sinkhole route via tailscale0), #18323 (tailscale's `net.ipv6.conf.all.forwarding = 1` instruction stops hosts accepting RAs), and #22403 (1.104.6, Mullvad + allow-LAN route-cap overflow). We run 1.104.6. Candidate next steps: report upstream with our repro (scapy src/dst matrix + `/proc/net/snmp6` counters + the stop-tailscaled control experiment), and/or test whether accepting RAs with `accept_ra = 2`, disabling the exit node on home-server, or a `TS_DEBUG_FIREWALL_MODE` override restores LAN/global IPv6.
- **External reachability test matrix** (use this instead of single curls): per domain, test IPv4+IPv6 from inside the LAN, via tailscale (`.ts.net` name), and from outside (e.g. `check-host.net/check-http` API, note it is IPv4-only). DNS A/AAAA records are kept current via dyndns; don't assume staleness without checking the host's actual address.
